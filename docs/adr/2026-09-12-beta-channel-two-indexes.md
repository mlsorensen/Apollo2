# Beta channel: a frozen stable index and a second merged index

- **Status:** Accepted
- **Area:** ota-release
- **First decided:** 2026-09-12 · **Last changed:** 2026-09-29
- **Boards:** all released boards

## Context

Pre-releases were wanted so a few devices could run a beta before promotion.
Every fielded device reads `releases.json` and installs the first entry that
is newer than itself. Firmware older than v0.14.0 parses a version with a
plain `sscanf("%d.%d.%d")`, which ACCEPTS `0.14.0-beta.1` and reports 0.14.0.
A beta listed in `releases.json` would therefore install itself on every
stable device as if it were the release of that number.

## Decision

Two indexes on the site, both newest first, generated by the `pages` job:

| File | Contents | Who reads it |
|---|---|---|
| `releases.json` | RELEASES ONLY; format frozen forever | every device not on the beta channel, the web flasher |
| `releases-beta.json` | releases AND pre-releases merged | devices with `Config::beta_channel` (NVS `updbeta`; Settings > Apollo > WiFi > Beta updates, shown only while the check cadence is not Off), the flasher with "Include pre-releases" |

A beta-channel device makes ONE fetch either way, and a stable release newer
than the last beta still wins. A 404 on the beta index (a site deployed
before it existed) falls back to the stable list.

Ordering lives in two places that must agree: `core::semver_newer()`
(`include/core/semver.h`, shared with the settings-backup version check) and
`order_key()` in the workflow's `pages` job. A release outranks every beta of
the same number; beta.2 outranks beta.1. Only `-beta.N` is understood; any
other pre-release form parses as "not newer" and is ignored rather than
guessed at.

CI publishes a `vX.Y.Z-beta.N` tag as a GitHub pre-release that never takes
the Latest badge, keeps it out of `releases.json` and `version.js`, and falls
back to the `## vX.Y.Z` changelog section for its notes. Betas accumulate on
`gh-pages` (`keep_files`); prune by hand if the list gets silly.

Promotion is a rebuild at the real tag (see the release-process record).
A copied beta binary would report its beta version forever and re-prompt.

## Evidence

- The parsing hazard is by construction, not observation: `parse_version()`
  in `update_check.cpp` rejects any tail it does not understand precisely
  because the older parser did not.
- v0.14.0-beta.1 to beta.4 (2026-09-12) exercised the channel on the bench
  units before v0.14.0 the same day; the 1.0 line ran eight betas from a
  branch (2026-09-22 to 2026-10-05) before v1.0.0 on 2026-10-10.
- 2026-09-29: the flasher page's script had died at load since the beta
  change (a `const` read in its temporal dead zone), leaving the version
  dropdown with one entry and Detect unbound. Found and fixed with a node
  smoke test against a mock DOM (`bcd7be1`).

## Alternatives and dead ends

- Widening `update_check_mode` with a "beta" value instead of a new key:
  rejected. An older build indexes its stored cadence into a fixed array,
  and OTA rollback puts an older build back unattended (see the NVS record).
- Teaching the flasher a separate page for betas: one page, one checkbox
  (or `?beta=1`) that swaps which index feeds the dropdown; cards,
  manifests and detection are identical.

## Consequences

- `releases.json` can never carry a pre-release or change shape. Any new
  per-release data goes in a per-tag file (`notes.txt`, `meta.json`).
- Turning the switch on drops the cached check result and re-checks, so the
  next notice matches the channel; a device already RUNNING a beta stays on
  it until a stable release passes it.
- The release checklist applies to betas unchanged, including the maintainer's
  approval click.
